# MasCloner v3.2.2 recovery-validation patch

v3.2.1 fixed the recovery inventory mismatch, but its verification read files
in manifest key order. That order can differ from physical archive order,
causing repeated decompression and a very long backup phase. v3.2.2 verifies
each file in archive order while retaining the complete SHA-256 and required
path checks. The published v3.2.0 and v3.2.1 tags and assets remain unchanged.

The reported v3.2.1 attempt was interrupted in phase `validated`, before the
bridge stopped services or changed the installation. The operator confirmed
both services active and `.commit_hash` still at
`7f22b48bd2c159d998120a39fd672e818910973a`. No migration or recovery
command is needed for that unchanged VM.

## Existing v3.0 installation

Once the [v3.2.2 GitHub release](https://github.com/ali-raaed31/mascloner/releases/tag/v3.2.2)
is published, download the bridge and archive from that release:

```bash
mkdir -p ~/mascloner-v3.2.2 && cd ~/mascloner-v3.2.2
curl -fL -O https://github.com/ali-raaed31/mascloner/releases/download/v3.2.2/upgrade_v3_2.py
curl -fL -O https://github.com/ali-raaed31/mascloner/releases/download/v3.2.2/mascloner-3.2.2.tar.gz
curl -fL -O https://github.com/ali-raaed31/mascloner/releases/download/v3.2.2/mascloner-3.2.2.tar.gz.sha256
sudo python3 ./upgrade_v3_2.py --release-archive ./mascloner-3.2.2.tar.gz \
  --sha256 "$(cut -d ' ' -f1 ./mascloner-3.2.2.tar.gz.sha256)"
```

The bridge checks the archive digest before importing its code. Creating the
backup still takes time on the VM, but validation now reads the compressed
archive in order. Services stay online until the backup is verified. On
success the bridge prints `Installed 3.2.2 (<commit>)`. Use `mascloner update`
only for later releases, after this bridge has succeeded.

If the bridge reports failed recovery after stopping services, inspect the
transaction record under `/var/backups/mascloner/transactions/` before
retrying.
